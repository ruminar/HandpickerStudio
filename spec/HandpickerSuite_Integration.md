# HandpickerStudio・HandpickerSuite 連携仕様書

- 文書改訂番号：Rev. 3（評価保存と削除予約取消の順序を更新）
- 対象アプリケーションバージョン：HandpickerStudio v0.1.0
- 対応文書：[HandpickerStudio 基本設計書](HandpickerStudio_BasicDesign.md)
- 対象：Studio（C# / .NET 10）とSuite（ComfyUI上のPython）、Suiteの削除スクリプト

## 1. 責務と共有対象

StudioはSuite未起動時も既存の評価を読み書きできる構成とする。Studioは生成後の画像整理とごみ箱によるCheckpoint廃棄を担当する。Suiteは生成時のCheckpoint選択、Tagger、Tag Export / Import、Refresh All、従来の削除予約を担当する。

| 対象 | 契約 |
|---|---|
| `data/checkpoint_statuses.json` | 評価の唯一の正本。現行のversion 1、`statuses`、Checkpoint相対パスのキーを維持する |
| `data/checkpoint_favorites.json` | Suiteのfavorite互換用データ。正本から再作成できる |
| `checkpoint_delete_queue.jsonl` | Suiteの削除予約と取消の履歴。Suiteインスタンス自身の `output/CheckpointHandpickerSuite/delete_scripts/` 配下にある |
| `delete_reserved_checkpoints.py`、`checkpoint_delete_plan.txt` | 予約から生成される実行入口と作業用一覧。実行時は最新の共有データを参照する |
| 排他ファイル・処理記録 | 同じ評価DBに対する排他、共有書き込みの互換性確認、実行中または復旧が必要な廃棄操作に使用する |

Studioの各プロジェクトは、同じSuite環境に属する評価DB、ComfyUIのCheckpoint相対パスを解決する基準ルート、Suite側の予約先を対応付ける。共用画像Outputから予約先を推測しない。複数のSuite環境が同じDBを参照する構成では、予約先と協調する更新者の範囲を一意に確認できた場合にだけ共有書き込みを有効にする。異なる物理Checkpointに同じDB・相対パスが割り当たる場合は更新・廃棄を止める。同じ実ファイルが異なる評価DB・キーで管理される場合も、共通の廃棄判定ができる構成に直すまで廃棄を保留する。

別PCへの評価移行には、Suite互換形式の評価JSONを使用する。要素は `file_name`、`file_size`、`tag` とし、評価DBの相対パスは移行先で解決する。Suiteの自動Importは規定名の最新JSONを読み込み、既存評価を維持する。ファイル名を明示したImportでは、確認した既存評価の上書きを許可する。移行で `delete` を取り込んでも削除予約は生成しない。

Studioはごみ箱への移動が確定したCheckpointを、評価DBの任意項目 `studio_deleted_checkpoints` にプロジェクトID別の履歴として保存する。評価移行JSONにはパスやプロジェクトIDを含まない履歴一覧を任意項目として格納し、既存の `evaluations` にも `delete` を含める。Suiteは従来の評価一覧を取り込める。Studio同士では履歴一覧も引き継ぐ。

## 2. Checkpointの識別と評価値

- 評価キーはComfyUIのCheckpoint基準ルートからの相対パスとし、区切りは `/` に正規化する。キーの大文字小文字を勝手に書き換えず、Windowsで同一実体に解決される表記違いや複数ルートからの重複解決は検知する。物理ファイルが一つに確定しない場合は更新・廃棄を保留する。
- `ckpt_name_safe` は相対パスから `.safetensors` を除き、ASCII英数字、`_`、`-` 以外の連続部分を `_` に置換する。先頭と末尾の `_` を取り除き、空なら `checkpoint` とする。safe名は画像の照合に使う。評価キーや削除対象ファイルの識別には相対パスと物理実体を使う。
- 現行順の `👑 god!` (`god`)、`💛 favorite`、`👍 nice`、`✔ keep`、`🗑 delete`、`— none` を両方で認識する。`none` は該当レコードの削除で表現する。`status`、`updated_at`、`ckpt_name_safe` と互換性のある追加フィールドを保持し、関係のない評価を変えない。`updated_at` は操作記録に使い、並行更新の勝敗判定には使わない。
- 外部での改名は評価キーの変更を伴う。旧キーの既存評価をsafe名や同名候補から新キーへ移さない。旧キーの削除予約は物理的な消失や対象の変更を確認して失効させる。外部消失に対するRefresh Allの既存方針どおり、消失が確実な `delete` を整理し、`god`・`favorite`・`nice`・`keep` は保持する。

## 3. 共有評価DBの読み書き

### 3.1 共通のプロセス間排他

DBと同じ物理ディレクトリに固定の排他ファイル `checkpoint_statuses.lock` を置く案とする。Windows上のC#・PythonがWin32 `LockFileEx` で同じファイルの先頭1バイトを排他取得する。評価DB本体は置換されるため、排他ファイルは運用中に置換・削除しない。パス文字列やPCごとの名前付きミューテックスに依存せず、別のUNC表記やドライブ割り当てでも同じ排他ファイルに到達することを検証する。プロセス終了時はOSによる解放を利用する。ロック取得は待ち時間を制限し、競合・切断・権限不足で取得できなければ通知して書き込みを中止する。SMBの再接続・ロック喪失時は新たに取得し、正本を読み直してから続行する。

起動時の初期化を含め、Tagger、Tag Importのコミット、Refresh Allの消失整理、Studioの書き込み、削除スクリプトと廃棄後処理で同じ規約を使う。Studioの確認画面、画像退避、Suiteの候補走査、Importの準備、ブラウザへの通知、OSごみ箱処理はDB全体の排他の外で行う。

`LockFileEx` の相互運用、2台間のSMB排他、排他中の切断、原子的置換とハンドルの共有設定は実機で確認する。相互運用が確認できない環境では共有書き込み・廃棄を保留する。 [Microsoft Learn の LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)

### 3.2 検証・差分更新・保存

1. 排他を取得して最新JSONを開き、形式、対応バージョン、`statuses`、各レコードと重複キーを検証する。破損、読込・検証失敗、対象共有との接続断、既存DBの消失では書き込みを中止する。空のDBを作れるのは、Suiteの新規環境として初期化が明示され、保存先と既存データがないことを確認できた場合に限る。既存の監視や移行中に見つからないDBは初期化しない。
2. 最新値を使って操作の前提条件を再評価する。Taggerのトグルと遷移制約、Importの最新値を優先する既存ルール、廃棄処理中の対象変更の禁止もこの時点で判定する。変更対象だけを書き換える。複数レコードを扱うImportはコミット時にまとめて評価する。
3. 同じディレクトリの一意な一時ファイルに完全なJSONをUTF-8で書き、flush・正常終了を確認し、原子的に置換する。排他を失った場合や置換結果が不明な場合は再読込して結果を検証する。確認できない結果を成功として通知しない。複数アプリ・同一プロセス内の経路も同じ順序で処理する。
4. favorite互換ファイルは正本の `favorite` から現行形式で再生成する。`god` は正本に保持する。正本のコミット後に互換データ更新だけが失敗した場合は「評価更新済み・互換データの再生成待ち」と記録し、次の起動・更新・修復で排他下の最新正本から再生成する。正本を古い内容に戻さない。

同じCheckpointへの通常の明示的な評価変更は、排他下で各操作の前提を満たしたコミット順で反映する。Importでは現在評価が `none` のもののみ設定し、異なる既存評価はConflictとして保持する。Tag Exportのportable identity、ファイル形式、タグの取込対象は既存仕様を維持する。

## 4. 外部更新の検知とCycler

- Studioは評価DBを監視し、ファイル置換・再接続・手動更新での変化を再読込する。監視通知が欠けてもプロジェクト切り替え・書き込み直前に最新値を使う。読込障害時は直近の正常値を更新不能として表示できる。
- Cyclerは `cycle()` の開始時に、候補抽出より前に、有効な評価スナップショットを取得する。候補抽出・評価表示は同じスナップショットを用い、候補ごとにネットワーク上のJSONを読み直さない。初期案は1実行につき1回読込とし、最適化は置換や通知欠落を確実に扱えることの実測後に検討する。
- 最後に反映したスナップショットとの差分を取り、レコード消失を `none` として扱う。既存の `_sync_tag_status_changes()` を活用し、Tagger・Preview・Cycler・タブ状態の更新と全タブ通知を共通化する。競合した読込結果が古い状態を上書きしないよう、反映順を管理する。失敗時は直近の正常状態を維持して評価の取得不能を通知し、正本には書き戻さない。正常値が一度も取れていない場合は、評価フィルターを使う実行で取得失敗を明示する。
- ComfyUIへのQueue登録、`onNodeCreated` / `onConfigure` の復元、選択順・フィルター、Local Listの優先順位、保持回数、シャッフル、モデル外部削除時の次候補選択は既存の契約を保つ。評価同期のためにCheckpoint読込や選択全体をグローバルロックしない。

## 5. `delete` 評価と削除予約

| 操作 | 評価と予約の方針 |
|---|---|
| Suite Taggerで `delete` へ | 既存の `none` 経由の制約を維持する。物理Checkpointが一意の場合は従来どおり予約を生成する |
| Studioで `delete` へ | ドラッグで直接変更できる。新規のSuite削除予約は作成しない案とする |
| Tag Importで `delete` を復元 | 論理評価のみを復元する現行仕様を維持する |
| `delete` を解除 | 対象の有効な予約IDを失効させる。再度 `delete` に変えても旧予約は復活しない |
| Studioで廃棄成功 | 対象の予約を失効させ、消失したファイルの `delete` レコードを整理する |
| Refresh Allで消失を確認 | 対象予約を失効させ、消失した `delete` レコードを整理する。切断・列挙失敗時は保留する |

正本JSONと予約JSONLは別ファイルである。Suiteスクリプトは、有効な予約ID、最新評価 `delete`、予約時と同じ物理Checkpoint、他の廃棄操作が進行していないことのすべてを確認してから実行する。既存予約ファイルの破損や読込不能は、有効な予約がないことの根拠にしない。Studioの評価変更・ImportおよびSuiteのImportでは、評価の保存を確定してから、同じ排他の中で旧予約を取り消す。取消だけが失敗した場合は評価の保存済みを明示する。保存失敗時は予約を変更しない。未失効の予約がある対象を `delete` へ変更する操作は保留する。Studioでは現在の `delete` 以外の評価を設定し直すと、取消を再試行できる。Suite Taggerの規則と予約作成は既存方式に従う。生成スクリプト・計画一覧の更新が遅れても実行時の照合を省略しない。

Suiteの削除スクリプトは、対話の前に候補を並べる既存の流れを維持し、承認後に同じ排他・対象単位の実行契約で予約と対象を再検証する。表示時の予約IDを使い、同じ相対パスの新しい予約へ暗黙に置き換えない。対象のファイル識別情報を持たない旧予約は自動で有効とせず、確認のうえ予約し直す。Suiteスクリプトの明示的な削除とサイドカー範囲は既存仕様を維持する案とし、Studioのごみ箱と画像退避はStudioからの廃棄範囲とする。

## 6. Checkpoint廃棄の最終処理と復旧

### 6.1 確認・退避中

Studioは基本設計書 §8.3 に従い、確認画面を出す時点でCheckpointファイルの実体とルート構成を記録する。候補の同一性にはファイルハンドルから取得したボリューム識別子・ファイルIDを使い、サイズ・更新時刻などで内容の変更も検出する。対象を一意に確認できない場合は廃棄を保留する。通常は全体ハッシュを取らない。

確認表示と画像退避中は評価の更新を許す。退避の結果には各有効ルートの確認範囲、完了・失敗・未確定、検査以降の変更の有無を残す。ルート設定変更や切断、生成中・所属不明の候補で退避結果を信頼できないなら最終処理に進まない。OFFのルートは対象外とする。

### 6.2 対象単位の排他と本体の処理

1. 共通排他下で最新評価、予約状態、退避結果の有効性、対象ファイルの実体を最終確認する。評価が `delete` 以外、Studioの確認時と実体が異なる、Suiteスクリプトの承認時と予約IDが異なる、同じ対象の処理が進行中、のいずれかなら中止する。
2. 同じDB・Checkpointキーに紐付く実行中の記録を、操作ID、対象ファイルの識別情報、元のパス、予定する一時移動先付きで確定してからDB全体のロックを解放する。以後、その対象の評価変更、予約変更、他経路の廃棄は完了か復旧まで待つかエラーを返す。無関係なCheckpointの書き込みを継続できる。復旧の引き継ぎには、元の実行が終了していることの確認を要する。
3. Studioは確認したファイルハンドルを使い、同一ボリュームの操作専用の場所へ上書きなしで対象ファイルを一時移動し、そのファイルをごみ箱へ移す案とする。一時移動先はCheckpoint・画像の走査の範囲外とし、元と同じファイル名を維持する。確認後に元パスが別実体に差し替わっても別実体を移動しない。一時移動先や共有上の同一性・排他を確認できない場合は保留する。Suiteスクリプトでも予約時のファイルと同じ実体だけに削除を適用し、サイドカーを扱う場合はその候補範囲と実体を承認時に確定して再検証する。
4. ごみ箱への移動を確認後、共通排他下で処理した実体に対応する `delete` を整理して保存し、旧予約を失効させる。同じパスが再利用されても新しい実体に旧予約・旧 `delete` を引き継がない。予約取消に失敗した場合は実行中の記録を残し、後処理から再試行する。archiveの `★` 付与・cache更新はDB排他の外で行う。

ハンドルに対する上書きなしの名前変更はWin32 `SetFileInformationByHandle` の `FileRenameInfo` を候補とする。Shell側は `IFileOperation` の `FOFX_RECYCLEONDELETE` を候補とし、ごみ箱へ送れない条件での動作、復元先、項目別の成功確認を実機で確かめる。 [ファイルID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) · [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) · [IFileOperationの設定](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags)

### 6.3 途中失敗・再開

- 本体の処理前に中止した場合は元のCheckpointを保持する。画像退避が済んでいればarchiveに残す。
- 一時移動後にごみ箱が利用できない、キャンセルしたなどの場合は、同じ実体を元のパスへ上書きなしで戻す。元パスが再利用されていたり接続不能だったりする場合は一時移動先に保存して復旧を案内する。ごみ箱からの復元でも一時移動先に戻る構成なら、元の位置への復元手順を示す。いずれも無断で完全削除しない。
- 結果が不明な場合は、元・一時移動先の実体、操作結果、接続状態を照合する。単に元パスにファイルがないことを成功の根拠にしない。成功を確認できるまで同じ対象の再廃棄と旧予約実行を禁止し、確認できた工程だけを再開する。

## 7. Suiteの改修範囲と移行

| 対象 | 必要な改修 |
|---|---|
| `_load_status_db()`・`_save_status_db()`・`_set_status()` | 空DBへのフォールバックを更新経路から解消し、厳密な読込、共通排他、差分更新、一意な一時ファイルによる置換、互換ファイルの修復を共通化する |
| Tagger・`_commit_tag_import()`・Refresh All | 最新値の確認・評価・予約処理を共通のコミット経路に移す。Refresh Allは切断と消失を区別する。Importの準備処理と競合ポリシーを保つ |
| `cycle()`・`_sync_tag_status_changes()` | 候補抽出前のスナップショット読込、外部差分と `none` の同期を追加する。選択ロジックや外部削除後の既存挙動は維持する |
| `_write_delete_script()`・予約管理 | 対象識別情報の保存、実行直前の再検証、処理中・失効・失敗時の取り扱い、旧版スクリプトからの切り替えを設計する |

現行SuiteのTag Transferはプロセス内での実行順序に依存する。外部Studioとの競合には共通排他が必要になる。現行の削除スクリプトも表示前の予約読込に依存するため、承認後の再照合を追加する。評価形式と既存の正常な選択動作は互換を保つ。

移行時は既存評価JSON・互換データ・予約を保全し、旧版のSuiteと旧スクリプトの実行を終了してからSuite連携版へ切り替える。予約先に生成された旧スクリプトを更新する。別の場所に保存した旧スクリプトは新しい排他に参加できないため、使用停止を運用条件とする。Suite側で連携版の導入を明示し、Studioはその情報と参照先を確認してから共有書き込みを有効にする。導入前は評価表示までとする。

## 8. 連携の受入観点と参照点

基本設計書のT05・T10〜T12・T20〜T26を両製品で実施する。特に以下はローカルと対応するSMB構成で確認する。

- 2プロセス・2台から違うCheckpointの評価を同時変更し、変更が両方保持される。同一キーへのTagger・Import・Studio操作では各操作の既存制約が適用される。
- 読込エラー、破損、切断、一時ファイル書込失敗、正本置換後の互換ファイル更新失敗、ロック保持中の強制終了から復旧できる。評価JSONを空で上書きせず、既存の `god` を保持する。
- 廃棄の確認・退避中に評価を取り消せる。確定処理中は対象だけがロックされる。ファイル・予約IDの入れ替わり、復元・再ダウンロード、旧版と並行利用する構成、および予約失効後のスクリプト実行を確認する。
- Cyclerの次回実行で外部評価と `none` を反映し、既存のLocal List・各モードと、外部から本体が消えた場合の次候補選択を維持する。
