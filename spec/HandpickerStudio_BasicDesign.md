# HandpickerStudio 基本設計書

- 文書版数：0.1.0（初版・設計レビュー用）
- 作成日：2026-11-24
- 対象：Windowsデスクトップアプリ HandpickerStudio および ComfyUI-CheckpointHandpickerSuite 連携改修
- ステータス：基本設計案。未決事項は第12章に記載する。

## 1. 目的・位置づけ

HandpickerStudioは、HandpickerSuiteで評価したCheckpointを軸に、複数のComfyUI環境で生成された画像を閲覧・選別・整理するWindowsアプリケーションである。汎用画像ビューワではなく、Checkpointの評価、生成成果の管理、代表サムネイルの設定、不要Checkpointの廃棄までを一つの作業環境で扱う。

HandpickerSuiteは生成時のモデル選択・評価を担当し、HandpickerStudioは生成後の閲覧・再評価・ファイル整理を担当する。双方の評価情報は共有する。ComfyUIを起動していない状態でもStudioを利用できる構成を目指す。

### 1.1 設計原則

- 元画像および既存のHandpickerSuite評価情報を正本とする。cacheと走査履歴は再構築可能な派生情報とする。
- 過去画像の整理結果はファイルシステム上に残し、Studio独自のデータベースに依存させない。
- 日常の画像選別は少ない操作で行えるようにする。Checkpointの物理削除だけは明示的な操作と確認を要求する。
- 複数のローカル・ネットワーク出力ルートを統合して表示し、物理的な保存先は各ルートに対応させる。
- 既存のHandpickerSuiteおよびCheckpointThumbnailExporterの仕様を尊重し、不要な再実装や既存動作の変更を避ける。

## 2. システム構成・責務分界

| 構成要素 | 責務 |
|---|---|
| HandpickerStudio | プロジェクト管理、参照ルート管理、評価変更、画像閲覧・削除、archive整理、cache管理、Checkpoint削除、代表サムネイル設定 |
| HandpickerSuite | ComfyUI上のモデル選択・評価・既存の削除予約機構、共有評価情報の取得・更新、ノード状態の同期 |
| CheckpointThumbnailExporter | 既存の画像照合・日付バケット走査・JPEG縮小処理の参考実装。Studioの実行時依存にはしない方針 |
| ファイルシステム | Checkpoint、生成元画像、archive、cache、設定・評価JSONの保存 |

Studioの実行ファイル名は `HandpickerStudio.exe`、リポジトリ名は `HandpickerStudio` とする。実装言語・UIフレームワーク・配布方式は未決定。

## 3. プロジェクト管理

プロジェクトはCheckpointの集合と、その画像参照条件を定義する論理的な作業環境である。例：Anima、Illustrious。画像出力ルートを排他的に所有するものではない。同じoutputを複数プロジェクトが参照できる。

### 3.1 管理項目

| 項目 | 内容 |
|---|---|
| Project ID | 名称変更に影響されない内部識別子（設計案） |
| プロジェクト名 | 任意の表示名 |
| Checkpoint参照先 | 対象モデル群の格納場所 |
| 評価情報参照先 | HandpickerSuiteの評価DBへの参照。相対パスの基準も識別可能にする |
| 画像参照ルート | 第4章のカード情報の集合 |
| cache保存先 | プロジェクト・ルート間で衝突しない保存場所 |

### 3.2 操作

プロジェクトの新規登録、編集、切り替え、登録解除を行う。上部の選択UIでプロジェクトを切り替える。最後に開いたプロジェクトを次回起動時に復元する案とする。登録解除では元画像・archive・Checkpointを削除しない。

アプリ起動時およびプロジェクト切り替え時には、対象プロジェクトの評価情報、Checkpoint一覧、cacheの整合性、走査状態を確認する。他プロジェクトのcacheや画像を削除対象にしてはならない。

## 4. 画像参照ルート管理

チェックボックス付きディレクトリツリー方式は採用せず、ルート登録方式とする。ルートごとにカードを表示し、有効／無効を切り替える。

| 項目 | 内容 |
|---|---|
| Root ID | 固定の内部識別子 |
| Name | 任意の表示名 |
| Output | 画像を走査するルート。配下を再帰的に対象とする |
| Archive | 当該ルートの過去画像の移動先 |
| Enabled | ON/OFF |
| 接続状態 | Online/Offline等。Enabledとは独立した状態 |

ローカルパス、ネットワークドライブ、UNCパスに対応する。ArchiveはOutputと同一ファイルシステム内に置くことを基本とし、高速なファイル移動を可能にする。別ボリュームや別共有の場合には同等の速度を保証しない。

| 処理 | ON | OFF |
|---|---|---|
| 画像走査・archive移動 | 実行 | 実行しない |
| cache構築・更新 | 実行 | 実行しない |
| メイン領域への画像表示 | 対象 | 対象外 |
| 既存cache・走査履歴 | 保持 | 保持 |

接続不能時は走査をスキップし、未接続をファイル消失とみなさない。登録解除では元画像・archiveを削除しない。重複ルート、親子関係のあるルート、archiveやcacheの走査対象への混入を防ぐための設定検証を行う（具体方式は詳細設計）。

## 5. 画面設計

### 5.1 メイン画面

IDE風の構成とする。

```text
+----------------------------------------------------------------+
| HandpickerStudio       Project: [ Anima             v ]        |
+-----+-------------------+--------------------------------------+
|     | CHECKPOINTS       | Model_A                              |
| [C] | favorite          | +--------+ +--------+ +--------+     |
| [R] |   Model_A         | | image  | | image  | | image  |     |
|     | nice              | +--------+ +--------+ +--------+     |
|     |   Model_B         | +--------+ +--------+ +--------+     |
|     | keep              | | image  | | image  | | image  |     |
|     |   Model_C         | +--------+ +--------+ +--------+     |
|     | delete            |                                      |
| [S] |   Model_D         |                                      |
+-----+-------------------+--------------------------------------+
| Project: Anima                          6 images / 2 selected  |
+----------------------------------------------------------------+
```

アクティビティバーでCheckpointビュー、ルート管理ビュー、設定を切り替える案とする。Checkpointビューは物理ディレクトリツリーではなく、評価別の論理一覧とする。評価未設定（none）の表示は第12章で確定する。

### 5.2 Checkpointビュー

- Checkpointは単一選択。選択時に有効なルートから対応画像を統合表示する。
- ドラッグ＆ドロップで評価を変更できる。評価変更時の確認ダイアログは不要。
- deleteへの移動は論理評価の変更であり、物理削除ではない。
- deleteに属するCheckpointのみ、右クリックメニューから物理削除できる。DeleteキーでのCheckpoint削除は提供しない。

### 5.3 画像一覧・個別ビューワ

メイン領域はcache画像によるサムネイル一覧とする。画像の複数選択、選択画像の削除、代表サムネイル設定を提供する。通常クリックで別ウインドウに個別画像を開く。Ctrl/Shiftによる複数・範囲選択、Ctrl+A、右クリックメニューは操作案とする。

個別ウインドウは元画像を表示し、一覧の表示順を基準に左右カーソルキーで前後へ移動する。Deleteキーで表示中の画像をごみ箱に送る。削除成功後は次の画像を表示し、末尾の場合は前の画像、画像がなくなれば閉じる案とする。Escで閉じる案とする。表示順・拡大縮小・ウインドウの詳細挙動は詳細設計で定義する。

## 6. 画像の保存構造と関連付け

### 6.1 保存領域

- output：生成直後の元画像。
- archive：過去の元画像をCheckpoint別に保存する領域。元画像は加工せず移動する。
- cache：一覧表示用JPEG画像。archiveと同じCheckpoint・相対パスの階層を持つ。本日画像も対象とする。

論理構成例（物理位置はルート設定に従う）：

```text
output/
  20261124/Model_B_00001.png
archive/Anima/Root01/
  ★Model_A/20261122/Model_A_00001.png
  Model_B/20261123/Model_B_00002.png
cache/Anima/Root01/
  scan_index.json
  Model_B/20261123/Model_B_00002.jpg
  Model_B/20261124/Model_B_00001.jpg
```

archive/cacheにおけるCheckpointディレクトリ名はHandpickerSuiteの `ckpt_name_safe` に準拠する。元のOutputルートからの相対ディレクトリ階層を維持する。archiveの元画像名・拡張子は変更しない。cacheのJPEG化による同名衝突への対応は詳細設計で確定する。

### 6.2 画像とCheckpointの関連付け

画像ファイル名にはCheckpoint名が含まれることを基本前提とする。CheckpointThumbnailExporterのsafe名生成・画像照合方式を参考にする。元のCheckpoint相対パスとsafe名を混同しない。複数Checkpointに一致する場合、safe名衝突、所属が不明な画像は自動移動・削除しない。他プロジェクトの画像にも手を付けない。

archive内はCheckpointディレクトリから対象を特定できる。cache画像から元画像（outputまたはarchive）を確実に特定する必要がある。対応情報の保持方式は第12章で確定する。

## 7. 走査・archive・cache管理

### 7.1 基本処理

プロジェクトを開いた際に対象Checkpoint一覧を取得し、有効かつ接続可能なルートの走査・整理を行う。ルートON時や手動更新時の走査も行う案とする。UIをブロックしないように処理を分離する。

| 対象 | archive | cache |
|---|---|---|
| 本日日付の画像 | 移動しない | 作成・更新 |
| 過去日付の対象画像 | 相対階層を維持して移動 | 作成・更新 |
| 整理済み画像 | そのまま保持 | 必要な場合のみ作成・更新 |
| 不明・他プロジェクトの画像 | 変更しない | 作成しない |

本日判定は日付ディレクトリを基本とする案。Exporterの有効な `YYYYMMDD` バケット判定を参考にする。日付不明のフォルダ、タイムゾーン、日付境界の扱いは未決事項とする。安全のため判定不能なものは自動archiveしない案とする。

移動先に同名ファイルがある場合は無断で上書きしない。失敗したファイルを処理済みとしない。outputからarchiveに移動しても対応するcacheの論理位置は変えず、再生成を避ける。

### 7.2 走査履歴JSON

CheckpointThumbnailExporterの永続source indexを参考に、プロジェクト・ルート単位で過去ディレクトリの走査履歴を持つ。共通outputに残る他プロジェクトの画像を毎回全走査することを防ぐ。

記録項目案：schema version、Root ID、Output/Archiveの識別情報、Checkpointカタログの識別情報、バケット相対パス、走査完了状態、走査後のディレクトリ状態、失敗・未解決状態。

| 状態 | 処理 |
|---|---|
| 本日 | 毎回の更新処理で走査対象 |
| 過去・未走査 | 走査・移動 |
| 過去・走査済み・変更なし | スキップ |
| 過去・走査後に変更あり | 再走査 |
| Checkpoint追加・照合条件変更 | 必要なバケットの無効化・再走査 |
| 移動失敗・アクセス不能 | 完了扱いにせず再試行可能にする |

移動による状態変化を含むため、完了記録は移動・空ディレクトリ削除の後の状態を基準にする。親ディレクトリの更新日時だけでは子孫の変更を確実に検知できないため、変更判定方式は詳細設計で検証する。JSONを失っても元画像を変更・破棄することなく再構築できるようにする。

### 7.3 空ディレクトリ削除

画像移動によって空になったディレクトリを、子から親へ順に自動削除する。全エントリが存在しない場合のみ非再帰的な削除を行う。Outputルートは削除しない。本日の日付ディレクトリは通常の整理で削除しない案とする。他プロジェクトの画像や非画像ファイルが残る場合は削除しない。対応する走査履歴も整理する。確認ダイアログは不要。

### 7.4 cache整合性

プロジェクトを開く際に、プロジェクト全体のcacheとCheckpointの関連付けを確認し、存在しないCheckpointに対応するcacheを削除する。参照ルートOFF、ネットワーク切断、Checkpoint一覧取得失敗を消失とみなさない。元画像の削除・変更が確実に確認された場合は対応cacheを削除・更新する。cache自体はごみ箱に入れる必要のない再生成可能なデータとする案。

## 8. ファイル削除とCheckpoint廃棄

### 8.1 画像削除

一覧からの複数画像削除、個別ウインドウのDeleteキーとも、元画像をWindowsのごみ箱へ移動する。Studio独自の確認ダイアログは出さない。成功した画像だけcache・一覧から除去する。失敗やキャンセル時は表示を維持し、結果を通知する。複数削除の部分成功を扱う。

### 8.2 Checkpoint削除

対象はdelete評価のCheckpointに限る。右クリックメニューで削除を実行し、確認ダイアログを表示する。生成済み元画像は削除しない。

処理順序案：

1. 削除対象と最新のdelete評価を再確認する。
2. 確認ダイアログを表示する。
3. 残存する対象画像をarchiveへ退避する（本日の画像も含める例外処理案）。
4. Checkpoint本体をごみ箱へ移動する。
5. 削除成功後、archive直下の対象Checkpoint名の先頭に `★` を付与する。
6. 対応するcacheを削除し、評価情報・一覧を更新する。

`★` は削除済みCheckpointの識別子であり評価マークではない。削除済みの画像はStudioのCheckpoint一覧から閲覧できなくなるが、archiveに保存され、エクスプローラーで閲覧できる。

退避失敗時はCheckpoint削除を中断する案とする。削除成功後の★付与・cache削除失敗は再試行可能にする。OFFまたはOfflineのルートに残る画像の扱い、関連サイドカーファイルの削除範囲、外部削除・復元時の扱いは未決事項とする。

### 8.3 ごみ箱利用上の制約

ローカル・ネットワークパスの種類やファイル容量等により、ごみ箱へ移動できない場合がある。Studio独自の通常削除確認と、OSの完全削除確認を区別する。無断の完全削除へのフォールバックは行わない。ごみ箱不可時の具体的なOS連携・中止方針は実装検証で確定する。

## 9. 代表サムネイル設定

画像一覧または個別ビューワの右クリックメニューから、選んだ画像に対応するcache JPEGをCheckpoint本体の隣へコピーする。

```text
Model_A.safetensors
Model_A.jpg
```

既存のサムネイルがあれば更新する。選定済みマーク、代表画像ID、専用の管理JSONは持たない。元画像の移動・削除後もコピー済みの代表画像は残る。

JPEG縮小仕様はCheckpointThumbnailExporterを参考にし、アスペクト比維持、拡大なし、最大辺・品質指定を基本とする。初期値案は最大辺512px、JPEG品質90。Exporterの管理用JPEGコメントは付与しない（Exporterのuninstall_managedによる手動選定画像の削除を防ぐ）。既存のHandpickerSuiteおよびOGN-ModelManagerのサイドカー参照規則に合わせる。既存の別拡張子サムネイルとの競合や再表示タイミングは詳細設計で確認する。

## 10. HandpickerSuiteとの評価情報連携

### 10.1 現行実装（議論時に確認したmainブランチ）

評価DBは `data/checkpoint_statuses.json`。Checkpoint相対パスをキーとし、status、updated_at、ckpt_name_safeを保持する。現行の `_set_status()` は最新JSONを読み、対象評価を変更して即時保存する。noneはレコード削除で表現する。`_get_status()` もJSONを読み込む。`_save_status_db()` はfavorite互換ファイルも更新する。

ブラウザ側は `onNodeCreated` / `onConfigure` を利用してSelectorの一覧取得、Tagger・Cycler等の状態復元を行う。Tag Importで利用される `_sync_tag_status_changes()` はバックエンド状態と全ブラウザタブへの変更通知を扱う。

### 10.2 連携方針

- 現行の評価DBを共有し、新たな評価の正本は設けない。
- Studioでの評価変更は対象Checkpointの評価を即時保存する方針とする。書き込み前に最新DBを取得し、他の評価を古い情報で上書きしない。
- ComfyUI側のTaggerによる即時保存および既存のワークフロー初期化処理を維持する。
- Cyclerの `cycle()` 冒頭、候補抽出より前に外部変更を検出し、必要な状態同期を実行する。現行の選択ロジックは変更しない。
- 更新日時を比較して新旧を判定する当初案は、現行の即時保存機構を踏まえて再整理する。通常のCycler実行時に古いメモリ情報をJSONへ書き戻す必要はない。
- 外部変更の差分にはnoneへの変更（レコード消失）も含める。既存の `_sync_tag_status_changes()` の活用を検討する。
- Checkpoint本体削除後の次候補選択は既存の削除スクリプト運用と同等の動作に委ねる。追加改修は原則不要とする。

### 10.3 整合性上の要件

評価DBの書き込みは双方で競合しないようにする。アトミックな置換だけではread-modify-writeの競合は解消しないため、共通排他方式または同等の競合防止策を詳細設計で決定する。ネットワーク経由の利用時も考慮する。破損・アクセス不能を空の評価DBとみなして上書きしない。

既存のfavorite互換情報と削除予約queueとの整合性を維持する。特にStudioでdeleteへ変更する際に既存の削除予約を作成するか、delete解除時に既存予約をどう取り消すか、Studio削除後の予約整理をどう行うかは未決事項である。Suiteの既存Taggerにはdelete遷移制約があるため、Studioの自由なドラッグ評価変更との整合性も確認する。

## 11. 非機能要件・異常系・受入観点

### 11.1 性能・操作性

- 一覧はcacheを利用し、表示範囲の仮想化・遅延読み込みを検討する。
- 大量画像の走査・JPEG生成・ネットワークアクセスでUIが操作不能にならないようにする。
- プロジェクト切り替えやルートOFF時に、旧対象の非同期処理が新しい画面に結果を反映しないようにする。
- ファイル操作の進捗・失敗を把握できるようにする。数値性能目標は実測後に定義する。

### 11.2 安全性

元画像とcacheの削除処理を区別する。パスの正規化とルート内判定を実施し、ジャンクション・シンボリックリンク・ネットワーク切断・重複ルートを考慮する。生成中・書き込み中の画像は破損や誤移動を防ぐ。既存ファイルを無断で上書きしない（明示的な代表サムネイル設定を除く）。

### 11.3 主要受入テスト

| ID | 観点 | 期待結果 |
|---|---|---|
| T01 | プロジェクト切替 | 対象Checkpointと画像だけが表示される |
| T02 | 共通output | Animaの整理でIllustriousの画像が変更されない |
| T03 | 複数ルート | 同じCheckpointの画像を統合表示。別ルートの同名画像が衝突しない |
| T04 | カードOFF/ON | OFFで表示・走査対象外、ONで再開。ファイルは失われない |
| T05 | ネットワーク切断 | 誤削除しない。再接続後に処理可能 |
| T06 | 本日・過去画像 | 本日画像はoutputに残り、過去画像はarchiveへ移動。両方cacheを作成 |
| T07 | 再走査 | 未変更の過去バケットをスキップ。変更・新規Checkpoint・失敗を再処理 |
| T08 | 空ディレクトリ | 空になった階層だけ削除。別画像や非画像ファイルを残す |
| T09 | 画像閲覧・削除 | 左右キー・複数選択・Deleteで所定動作。確認なし、ごみ箱利用 |
| T10 | Checkpoint削除 | delete以外は削除不可。確認あり。元画像保持、★付与、cache削除 |
| T11 | 評価変更 | StudioとSuiteが評価を共有。次回Cycler実行で外部変更を反映 |
| T12 | 競合 | 同時評価変更で別Checkpointの評価を失わない |
| T13 | 代表サムネイル | cache JPEGを既存規則のサイドカーへコピー。マークや専用DBなし |
| T14 | cache再構築 | cache・走査JSON消失後も元画像を保ったまま再構築可能 |
| T15 | 異常系 | 移動・削除・JSON更新の失敗を成功扱いにしない。無断完全削除なし |
