- 文書改訂番号：Rev. 29（Archive化・解除後の空フォルダー削除）
- 対象アプリケーションバージョン：HandpickerStudio v0.1.0
- 作成日：2026-11-24
- 対象：Windowsデスクトップアプリ HandpickerStudio および ComfyUI-CheckpointHandpickerSuite 連携改修

## 1. 目的・位置づけ

HandpickerStudioは、HandpickerSuiteで評価したCheckpointを軸に、複数のComfyUI環境で生成された画像を閲覧・選別・整理するWindowsアプリケーションである。汎用画像ビューワではなく、Checkpointの評価、生成成果の管理、代表サムネイルの設定、不要Checkpointの廃棄までを一つの作業環境で扱う。

HandpickerSuiteは生成時のモデル選択・評価を担当し、HandpickerStudioは生成後の閲覧・再評価・ファイル整理を担当する。双方の評価情報は共有する。ComfyUIを起動していない状態でもStudioを利用できる構成を目指す。

### 1.1 設計原則

- 元画像および既存のHandpickerSuite評価情報を正本とする。cacheと走査履歴は再構築可能な派生情報とする。
- 過去画像の整理結果はファイルシステム上に残し、Studio独自のデータベースに依存させない。
- 日常の画像選別は少ない操作で行えるようにする。Checkpointの物理削除だけは明示的な操作と確認を要求する。
- 複数のローカル・ネットワーク出力ルートを統合して表示し、物理的な保存先は各ルートに対応させる。
- 既存のHandpickerSuiteおよびCheckpointThumbnailExporterの仕様を尊重し、不要な再実装や既存動作の変更を避ける。

### 2.1 実装・ビルド・配布

- 初期リリースの配布形式はWindows x64向けのポータブルZIPとし、ランタイムの配布方式はFramework-dependentとする。.NET 10 Windows Desktop Runtime（x64）の事前インストールを利用条件とし、.NETランタイムはZIPに含めない。HandpickerStudio自体のインストーラーは作成しない。ユーザーが書き込めるフォルダに展開し、標準ユーザー権限で `HandpickerStudio.exe` を起動できるようにする。
- 設定・プロジェクト登録・重複保留などのStudio管理情報は、原則として `AppContext.BaseDirectory` を基準にアプリケーション配下へ保存する。書き込めない場合は保存先を知らせ、書き込み可能な場所への展開を案内する。archive・cacheの保存先は第3・4・6章のルールを適用する。共有評価DBと削除予約の配置は連携仕様書に従う。
- OpenGepaのPowerShellスクリプトを参照し、`dotnet publish` に `-c Release`、`-r win-x64`、`--self-contained false` を明示する。発行結果の確認、README等の配布文書の配置、バージョンと対象環境を名前に含むZIPの生成を再利用する。MCP対応は対象外とし、発行対象はHandpickerStudioのWPFプロジェクトに限る。実行ファイル、必要な配布文書とライセンス文書を収録し、ZIPの内容を検証する。
- 配布READMEには利用条件の .NET 10 Windows Desktop Runtime（x64）と、Microsoft公式ページの「.NET Desktop Runtime」からWindows x64を選ぶ手順を記載する。 [Microsoft公式の .NET 10 ダウンロード](https://dotnet.microsoft.com/en-us/download/dotnet/10.0)
- ビルドはリポジトリ内の成果物専用領域に毎回新しい発行用フォルダを作る。既存の展開・運用フォルダを出力先や掃除対象に使わず、archive・cacheやSuite側の共有データにも書き込まない。利用中の設定JSONや管理データを配布物に含めず、初期値を同梱する場合は利用中の設定と別ファイルにする。発行とZIPの検証が完了してから配布成果物を公開し、失敗時は直前の有効な成果物を保持する。
- 実装開始の指示後、機能実装に先立ちHandpickerStudio用のビルドスクリプトを整備する。既存の空のWPFアプリでビルドとZIP生成を行い、.NET 10 Windows Desktop Runtime（x64）導入済みのWindows 11 x64で、展開先から標準ユーザー権限で起動・終了できることを確認する。再ビルドや失敗時に既存の設定・管理データが残ることも確認したうえで、機能実装へ進む。

## 3. プロジェクト管理

プロジェクトはCheckpointの集合と、その画像参照条件を定義する論理的な作業環境である。例：Anima、Illustrious。画像出力ルートを排他的に所有するものではない。同じoutputを複数プロジェクトが参照できる。

現行運用では `ComfyUI/jpeg_output` を共用する。`ComfyUI/Anima` と `ComfyUI/Illustrious` はそれぞれ `ComfyUI_models/checkpoints` と `ComfyUI_windows_portable` を持つ。Animaはほかに `diffusion_models`、`loras`、`text_encoders`、`vae`、Illustriousは `loras` を持つ。`ComfyUI/_Common/ComfyUI_models/upscale_models` は共有領域である。画像の保存ワークフローと既存画像のメタデータは現行のままとする。

### 3.1 管理項目

| 項目 | 内容 |
|---|---|
| Project ID | 名称変更に影響されない内部識別子 |
| プロジェクト名 | 任意の表示名 |
| ComfyUIフォルダー | ポータブル版の外側のフォルダー、またはComfyUI本体のフォルダー。指定するとCheckpointと評価情報の参照先を検出する |
| Checkpoint参照先 | ComfyUIの標準フォルダーと追加設定から検出したモデル格納場所。従来の手動指定も利用可能 |
| 評価情報参照先 | HandpickerSuiteの評価DBへの参照。相対パスの基準も識別可能にする |
| 画像参照ルート | 第4章のカード情報の集合 |
| アーカイブ設定 | 起動時の自動実行と初回確認の状態 |
| cache保存先 | プロジェクト・ルート間で衝突しない保存場所 |

### 3.2 操作

プロジェクトの新規登録、編集、切り替え、登録解除を行う。上部の選択UIでプロジェクトを切り替える。最後に開いたプロジェクトを次回起動時に復元する案とする。登録解除では元画像・archive・Checkpointを削除しない。

ComfyUIフォルダーを指定すると、本体の `extra_model_paths.yaml` を読み、`models/checkpoints`、追加の `checkpoints`、CheckpointSave用の `output/checkpoints` をComfyUIと同じ優先順に並べる。`is_default: true` を指定した参照先は標準フォルダーより優先する。設定画面には存在する参照先のみを `パス (件数)` の形式で表示し、件数はサブフォルダーを含めてStudioが対象とするCheckpointを数える。一部を走査できなかった場合は `(件数+)` で確認できた件数を示す。検出した参照先の構成をプロジェクトのモデル一覧に使う。手動設定済みのプロジェクトも利用できる。追加設定を変更した場合はプロジェクト設定から再検出できる。

既定および追加の `custom_nodes` では、Manager版 `checkpoint-handpicker-suite` とGit版 `ComfyUI-CheckpointHandpickerSuite` の `data` を確認し、評価JSONとStudio連携情報の有無を表示する。利用可能な評価JSONが一つなら自動選択し、複数ある場合は使用するものを選択する。同じCheckpoint相対パスが複数の参照先にある場合、表示は優先順の先頭を使い、その評価キーが共有される操作を保留する。

アプリ起動時およびプロジェクト切り替え時には、対象プロジェクトの評価情報、Checkpoint一覧、cacheの整合性、走査状態を確認する。他プロジェクトのcacheや画像を削除対象にしてはならない。

プロジェクト設定の「アーカイブ設定」に続く「評価の移行」タブで、保存済みのプロジェクト設定を使い、Checkpoint評価を `プロジェクト名_YYYYMMDD_HHMMSS.json` にエクスポートする。形式はSuite互換の `format_version: 1` とし、評価済みCheckpointのファイル名、バイト数、評価を格納する。別PCのStudioでは選択中のプロジェクトで一致先が一意なものを取り込む。既存評価が変わる場合は件数を示して確認し、一致なし、複数一致、確認後に変わった対象はスキップする。プロジェクト設定やパス、削除予約は転送しない。

Studioで今後ごみ箱への移動が確定したCheckpointは、プロジェクト単位でファイル名とバイト数を評価DBの履歴に残す。エクスポート時に廃棄履歴を含めるか選択でき、初期状態では含める。含める場合は廃棄済みのモデルを移行JSONに `delete` として格納し、Studio間で履歴自体も移行できるようにする。同じファイルに現在の明示的な評価があればそちらを優先し、履歴を選択解除した場合も現存するCheckpointの評価は書き出す。取り込み先の既存評価と廃棄履歴に照合・統合する。移行によるCheckpointの廃棄や削除予約の生成は行わない。

### 3.3 Checkpoint名の重複検査

プロジェクト作成・Checkpoint参照先の変更時に、対象プロジェクト内と登録済みの他プロジェクトのCheckpoint一覧を照合する。起動、プロジェクト切り替え、手動更新、Checkpoint一覧の変更検知時にも検査する。定期的な全画像走査を重複検査のために追加する必要はない。取得できなかった一覧は空として扱わず、未確認と表示する。共用Outputでは、確認できる保存形式について保存ノードがsafe名を変換した後のラベルの衝突も検査する。

プロジェクト間の画像ラベル衝突は、同じOutputまたは親子関係のあるOutputで重なる範囲に限る。画像ごとにその保存場所を参照するプロジェクトのCheckpointを照合する。参照ルートの有効・無効は走査の切り替えに用い、共用Outputにすでに存在する画像の候補からは除外しない。

警告には該当する全プロジェクト名、`ckpt_name_safe`、Checkpointのフルパスを表示し、まとめてクリップボードへコピーできるようにする。登録は継続可能とし、対象画像の扱いは §6.2 に従う。Checkpointの改名はユーザーがエクスプローラー等で行う。改名に伴うSuiteの評価・削除予約の扱いは[連携仕様書](HandpickerSuite_Integration.md)を参照する。

## 4. 画像参照ルート管理

チェックボックス付きディレクトリツリー方式は採用せず、ルート登録方式とする。ルートごとにカードを表示し、有効／無効を切り替える。

| 項目 | 内容 |
|---|---|
| Root ID | 固定の内部識別子 |
| Name | 任意の表示名 |
| Output | 画像を走査するルート。配下を再帰的に対象とする |
| Archive | 当該ルートの過去画像の移動先 |
| Enabled | ON/OFF |
| 接続状態 | Online/Offline等。Enabledとは独立した状態 |

Archiveが空欄の場合は、Outputを選択したときに末尾の区切りを除き、フォルダー名に `_archive` を付けた兄弟フォルダーを設定する。Outputを手入力して保存する場合も空欄には同じ初期値を使う。設定済みのArchiveは編集できる。保存後、有効なルートのOutputに接続できる場合に、必要なArchiveフォルダーを作成する。

ローカルパス、ネットワークドライブ、UNCパスに対応する。ArchiveはOutputと同一ファイルシステム内に置くことを基本とし、高速なファイル移動を可能にする。追加・変更した有効な参照ルートのOutputとArchiveが別ボリュームまたは別共有に見える場合、保存前にコピーと元画像の削除について警告し、設定の保存を続けるか確認する。

| 処理 | ON | OFF |
|---|---|---|
| 画像走査・archive移動 | 実行 | 実行しない |
| cache構築・更新 | 実行 | 実行しない |
| メイン領域への画像表示 | 対象 | 対象外 |
| 既存cache・走査履歴 | 保持 | 保持 |

接続不能時は走査をスキップし、未接続をファイル消失とみなさない。登録解除では元画像・archiveを削除しない。同一プロジェクト内の実体が重なるOutput登録、archiveやcacheの走査への混入を設定時に防ぐ。プロジェクトをまたぐ共通Outputは物理的な範囲が確認できる場合に登録できる。UNC・ドライブ割り当て・ジャンクションなどで同じ範囲を参照する場合も共通Outputとして扱う。関係を確定できない範囲の自動ファイル変更は保留する。

## 5. 画面設計

### 5.1 メイン画面

IDE風の構成とする。

```text
+--------------------------------------------------------------+
| HandpickerStudio  [ Anima v ]                       表示設定 |
+-----------------------+--------------------------------------+
| Checkpoint  参照ルート | Model_A                    [タイル v] |
| ▸ god!            0   | +--------+ +--------+ +--------+     |
| ▾ favorite        1   | | image  | | image  | | image  |     |
|   Model_A             | +--------+ +--------+ +--------+     |
|          ───          | +--------+ +--------+ +--------+     |
| ▸ nice            2   | | image  | | image  | | image  |     |
| ▸ keep            0   | +--------+ +--------+ +--------+     |
| ▸ delete          0   |                                      |
| ▾ none           32   |                                      |
|   Model_B          ▒  |                                      |
| 所属未確定 (0)        |                                      |
+-----------------------+--------------------------------------+
|                                                         6 枚 |
+--------------------------------------------------------------+
```

Checkpointと参照ルートはタブで切り替える。所属未確定の画像はCheckpointタブ下部のボタンから確認できる。上部の「表示設定」でライト・ダーク・システムに合わせるを選べる。外観はアプリ全体に反映し、アプリ配下の設定に保存する。従来の設定で外観が未指定の場合はライトを使う。

メインウインドウの通常時の位置・サイズと最大化状態を、終了時にアプリ配下の設定へ保存し、次回起動時に復元する。最小化して終了した場合は、最小化する前の通常表示または最大化で起動する。モニター構成が変わり保存位置が画面外になった場合はWindowsの表示位置補正を使う。

### 5.2 Checkpointビュー

- CheckpointはCtrl＋クリックで複数選択でき、別の評価ペインの項目も同時に選べる。Shift＋クリックで同じペイン内の範囲を選択する。右側には現在のCheckpointの画像を表示する。評価を変更しても選択と画像一覧を引き継ぐ。
- 空の評価も含め、`👑 god!`、`💛 favorite`、`👍 nice`、`✔ keep`、`🗑 delete`、`— none` の順にペインを縦に並べる。見出しに件数を表示し、クリックで開閉できる。各一覧は独立して縦にスクロールし、展開済みのペイン間の境界をドラッグして高さを調整できる。初期表示では件数の多い `none` に残りの高さを割り当てる。
- 各ペイン内では、ComfyUIのWindows版と同じく、フォルダー名を含むCheckpointの相対パスを大文字・小文字を区別してUnicodeコードポイント順に並べる。
- 一覧の末尾で下キーを押すと次の展開済みペインの先頭へ、先頭で上キーを押すと前の展開済みペインの末尾へ移動する。項目が空のペインは飛ばす。
- Checkpointの行にポインターを置くと、ツールチップにファイルパスと代表画像を表示する。代表画像は同じフォルダーにある既存のサムネイルから取得する。右側の画像一覧に表示中のCheckpointと、代表画像がないCheckpointはファイルパスだけを表示する。複数選択中も、右側に表示している1件にこの制限を適用する。
- 選択したCheckpointをまとめて各評価の見出しと一覧へドラッグ＆ドロップできる。空や折りたたんだペインも見出しでドロップを受け付ける。評価変更時の確認ダイアログは不要。同じ評価の項目はそのままにし、処理できない項目があれば知らせる。`none` は未評価を表す。
- deleteへの移動は論理評価の変更であり、物理削除ではない。
- deleteに属するCheckpointを1件選択しているとき、右クリックメニューから物理削除できる。DeleteキーでのCheckpoint削除は提供しない。

### 5.3 画像一覧・個別ビューワ

メイン領域には元画像のサムネイルを一覧表示し、画像キャッシュが有効な場合は保存済みのサムネイルを再利用する。表示形式は一覧、タイル、画像だけのタイル(簡易)から選ぶ。タイル表示ではCtrl＋ホイールで大きさを調整できる。画像の複数選択、選択画像の削除、別プロジェクトへの移動、代表サムネイル設定を提供する。クリックで選択し、ダブルクリックで別ウインドウに個別画像を開く。Ctrl＋クリックで個別に、Shift＋クリックで範囲を選択できる。別プロジェクトへの移動は一覧の右クリックメニューから実行する。

表示形式を切り替えても選択中の画像を維持する。どの表示形式でも、選択中の画像に枠を付け、右上の橙の斜め帯に白い輪郭の星を表示する。

個別ウインドウは元画像を表示し、一覧の表示順を基準に左右カーソルキー・マウスホイールで前後へ移動する。画像表示領域をダブルクリックすると、ウインドウを現在のモニターの作業領域の高さに合わせ、画像の縦横比に応じた幅で表示する。幅が足りない画像も画面内に全体を表示する。再度ダブルクリックすると元の位置とサイズに戻る。Deleteキーで表示中の画像をごみ箱に送り、操作成功後は次の画像に移って引き続きDeleteを受け付ける。末尾では前の画像へ移り、画像がなくなれば閉じる。Escで閉じる。

## 6. 画像の保存構造と関連付け

### 6.1 保存領域

- output：生成直後の元画像。
- archive：過去の元画像をCheckpoint別に保存する領域。元画像は加工せず移動する。
- cache：一覧表示用の縮小PNG。表示設定で有効にしたときに必要な画像から生成する。既定は無効。保存先はプロジェクトの設定を使い、空欄の場合はアプリ配下の `cache` とする。

論理構成例（物理位置はルート設定に従う）：

```text
output/
  20261124/Model_B_00001.png
archive/Anima/Root01/
  ★Model_A/
    _checkpoint.json
    20261122/Model_A_00001.png
  Model_B/
    _checkpoint.json
    20261123/Model_B_00002.png
cache/HandpickerStudio-previews-v1/<install-id>/
  .handpickerstudio-owner
  <project-id>/<preview-key>.png
```

archiveの名前空間には変更されないProject ID・Root IDを使う。Checkpointディレクトリ名はHandpickerSuiteの `ckpt_name_safe` を基本とし、同一safe名や既存の `★` 付きディレクトリと衝突するときは別名で共存させる。元のOutputルートに対する相対階層と元画像のファイル名・拡張子を維持する。

archiveの所属は配置先のプロジェクト・ルートおよびCheckpointディレクトリの所属情報で決まる。`_checkpoint.json` はフォルダ単位で元のCheckpoint相対パスと所属を識別する。Archive化した画像の元のOutputは §7.2 の移動記録で管理する。手動移動した画像はファイル名を再照合せず、cacheを失った場合も配置先から復元する。旧形式のarchive、外部変更で所属を確認できないフォルダ、改名で対応先を失ったフォルダは要確認として一覧に出し、元画像を保持する。`★` 付きのarchiveを再ダウンロードされた同名モデルへ自動で再結合しない。

### 6.2 画像とCheckpointの関連付け

Checkpointの識別にはプロジェクト・評価DBの範囲とComfyUIから見た相対パスを用いる。`ckpt_name_safe` はSuite互換の照合用ラベルで、衝突検査では大文字小文字を区別しない。たとえば `a/b.safetensors` と `a_b.safetensors` はともに `a_b` となる。

- Output画像の照合は、保存済みのファイル名・相対ディレクトリだけを利用する。Exporterの一致判定は表示候補の発見に活用できる。自動移動を許すのは、既存保存形式に基づく完全なラベル照合で、そのOutput範囲を参照する全登録プロジェクトのカタログから帰属先を一意に決められる場合に限る。たとえばGM Image Saverは連続した `_` を一つにするため、Suiteでは異なる `a__b` と `a_b` が保存後に衝突する。部分一致、順位だけで選ばれた候補、区切りや切り詰めでラベルを特定できない画像は手動確認に回す。カタログや物理範囲を確認できない共通Outputでは自動移動を保留する。
- 重複を検知したsafe名と対応する保存ラベルを、影響する物理Output範囲とともにプロジェクト設定側の保留情報に記録する。記録の保存前は対象範囲の自動移動を保留する。構成やカタログが更新された場合は、進行中の走査処理もファイル変更前に対象の判定を見直す。初期案では、改名・登録解除で重複が解消しても旧ラベルに一致する画像を保留し続ける。確実に判別できる新しいラベルは通常処理に戻せる。旧ラベルを再利用する場合の保留解除は手動承認の要否も含めて第12章で確定する。画像の更新日時だけでは新旧を判定しない。保留情報は再構築可能な走査履歴とは別に保存する。保留情報を読み込めない、または履歴不明の既存共用Outputを新規登録する場合は、設定復元またはユーザーによる確認まで自動移動を保留する。登録前に解消された重複は現行カタログだけでは識別できない。
- 所属未確定一覧では、有効・接続中のOutputにある該当画像と、所属を確認できないarchive内の画像を閲覧できる。元パス、ルート、判定理由、判明している候補を表示する。画像のプロジェクトを明示して、ファイル名から所属を再照合できる。同じプロジェクトを選ぶ場合も同じ照合条件を使う。所属未確定の状態では画像削除や代表サムネイル選定を提供しない案とする。
- 旧版で記録された保留は、当時の共用範囲を確定できない場合も保持する。現在の候補が同じプロジェクト内で一意で、共用範囲に基づく保留がない画像は、右クリックで該当ラベルの旧版の保留を確認して解除できる。解除は保留情報と表示を更新し、画像ファイルは移動しない。
- cacheはStudioの管理専用フォルダーにインストール識別子とプロジェクトIDで分けて置く。元画像のフルパス、ファイル情報、縮小サイズが一致するcacheを再利用する。cacheを無効にすると、過去に利用した保存先も含め、その設定のStudioが作ったキャッシュを削除する。削除できなかった保存先は、無効のまま次回起動した際に再試行する。

## 7. 走査・archive・cache管理

### 7.1 Archive化の操作

Archive化は、Outputに混在している前日までの画像をCheckpoint別のフォルダーへ移し、エクスプローラーで必要な成果物を取り出せるようにする操作とする。通常の走査や「更新」は一覧を読み直す。

- プロジェクト設定では「参照ルート」「サムネイル」「アーカイブ設定」「評価の移行」の順に配置する。「Archive実行」「Archiveを戻す」「Archiveを開く」と、「アプリ起動時に自動でArchiveを実行します」の設定を用意する。各ボタンは保存済みの参照ルートを使う。
- Checkpointの右クリックに「アーカイブ化」「アーカイブ化解除」を用意し、選択中の複数Checkpointに適用する。日々の出力で同じCheckpointにOutputとArchiveの画像が混在するため、両方の項目を表示する。
- 初回にプロジェクト単位で確認し、同意を保存する。移動が別ボリューム・別共有をまたぐ場合は §8.2 のコピー確認も行う。
- 自動実行は既定でOFF。ONの場合はアプリ起動時に開いたプロジェクトで一度実行する。Archiveを戻す操作では、実行前に対象プロジェクトの自動実行をOFFにして保存する。
- 有効で接続中のOutputから、§6.2 の照合で対象Checkpointに所属が一意に決まった画像を移動する。Output内の相対階層と名前を保つ。ローカル日付で有効な YYYYMMDD のフォルダーを含み、日付フォルダーとファイルの最終更新日がすべて前日以前の画像を対象とする。生成中、日付を判定できない画像、所属未確定の画像は元の場所に残す。
- 処理はバックグラウンドで行い、移動・復帰の件数、競合や接続などで処理できなかった理由を表示する。移動先の同名ファイルは上書きしない。画像移動後のcacheは §7.4 に従う。

### 7.2 復帰用の移動記録

Archive化で移動する画像ごとに、プロジェクト、参照ルート、Checkpoint相対パス、移動前後の画像パス、ファイル識別情報をアプリケーション配下の `archive-history` に記録する。ファイルを移動する前に記録を保存し、復帰時には現在の参照ルートとArchiveに残っている画像を確認する。

「Archiveを戻す」「アーカイブ化解除」では、過去の実行分も含め、記録と一致する画像を元のOutput相対パスへ戻す。エクスプローラーで別の場所へ取り出した画像や、ごみ箱へ移した画像は復元しない。別の画像に置き換わった場合、移動先に同名ファイルがある場合、参照ルートを確認できない場合は報告し、確認できた画像だけ処理する。「プロジェクトへ移動」で振り分けた画像とCheckpoint廃棄で `★` を付けたArchiveは復帰対象外とする。

### 7.3 空ディレクトリ

Archive化・解除で画像の移動に成功した後、移動元の空フォルダーを子から親へ順に削除する。操作で画像を移動したフォルダーとその祖先を対象とし、OutputとArchiveのルート、リンク、他のファイルやフォルダーが残る階層は保持する。解除で空になったCheckpointのArchiveフォルダーに、対応するStudioの所属ファイル `_checkpoint.json` だけが残った場合は、所属ファイルとともに削除する。各フォルダーは非再帰的に削除し、削除できなかった場合は結果に表示する。

### 7.4 cache整合性

Studioで画像のごみ箱移動・振り分け・廃棄時の退避やarchiveの改名が成功したら、移動元の画像パスに対応する縮小画像を当該プロジェクトのcacheから個別に取り除く。元画像の操作に失敗した項目はcacheを保持する。cacheの清掃失敗は元画像の操作結果と区別する。

プロジェクトを開く際に、プロジェクト全体のcacheとCheckpointの関連付けを確認し、存在しないCheckpointに対応するcacheを削除する。参照ルートOFF、ネットワーク切断、Checkpoint一覧取得失敗を消失とみなさない。元画像の削除・変更が確実に確認された場合は対応cacheを削除・更新する。cache自体はごみ箱に入れる必要のない再生成可能なデータとする案。

## 8. ファイル削除とCheckpoint廃棄

### 8.1 画像削除

一覧からの複数画像削除、個別ウインドウのDeleteキーとも、元画像をWindowsのごみ箱へ移動する。Studio独自の確認ダイアログは出さない。成功した画像だけcache・一覧から除去する。失敗やキャンセル時は表示を維持し、結果を通知する。複数削除の部分成功を扱う。

### 8.2 画像のプロジェクト間移動

画像一覧と所属未確定一覧で単一・複数選択に対応する。右クリックの「プロジェクトへ移動」から移動先のプロジェクトと参照ルートを選ぶ。画像のファイル名に含まれる保存ラベルを、選択されたプロジェクト内のCheckpointと照合し、各画像を一意に対応するCheckpointのarchiveへ移動する。一致先なし・複数一致・移動先一覧が未確認の画像は元の場所に残す。実行前に移動できる枚数と対象外の枚数、プロジェクト・ルートを表示する。実行直前の再照合で候補が変わった画像は移動しない。移動先は有効かつ接続中で、書き込み可能なarchiveを持つルートに限る。

元画像は移動先Checkpointのarchiveに配置する。画質と埋め込みメタデータを保つため、デコード・再エンコードをせず元のファイル内容を維持する。評価情報には触れない。archive内の元画像を移す場合も、すでに保存された元Output由来の相対階層を引き継ぐ。移動先での所属は §6.1 に従う。

ファイル単位で次の順に処理する。通常の自動archiveと廃棄時の画像退避にも同じ安全条件を適用する。

1. 元画像の実体・変更状態と、移動元・移動先の範囲を検証する。走査、個別削除、手動移動などStudio内の競合操作をファイル単位で直列化し、古い一覧のパスだけを信用しない。
2. 同一ファイルシステムでは上書き禁止の移動を使う。別ボリューム・別共有のためにコピーへ切り替えるときは、実行中の操作につき最初のコピー前に確認する。承認後、移動先と同じ領域の一時ファイルにコピーし、コピーの完了、書き込みの確定、バイト数と元ファイルの同一性を確認してから、上書きなしで公開する。元画像は公開を確認した後に、コピーした実体と同一と確認できた場合のみ取り除く。全ファイルのハッシュ計算は通常処理に含めない。
3. 移動先公開後に切断等で元画像を除去できなかった場合は成功にせず、両方のファイルを保持して「要確認」とする。必要な処理記録は移動元・移動先と同一性の確認に絞る。復旧時に移動先を検証できない場合は元画像を削除しない。衝突したファイルは元側に残し、正常に移動できる別画像は続行する。
4. 成功分は移動元一覧／cacheから取り除き、移動先一覧に反映する。対象バケットとcacheの対応を更新または無効化し、再走査分だけ再構築する。派生情報の更新失敗は実ファイルの移動成功と区別して表示する。結果は成功・失敗・要確認をファイル単位で通知する。

### 8.3 Checkpoint廃棄

対象は `delete` 評価のCheckpoint本体に限る。右クリックから実行し、対象Checkpointのフルパスと退避対象ルートを示して確認する。元画像は保存する。

1. 確認前にCheckpointの実体、評価参照先、対象ルートの構成を記録する。OFFルートは退避・変更の対象から外し、確認画面にその旨を表示する。ONでOutputまたはarchiveがOffline・確認不能なら、退避未確認として廃棄を保留する。
   ComfyUIのCheckpointSave用の `output/checkpoints` が未作成で、親の `output` を確認できる場合は、モデルの照合対象から外す。作成済みなら照合に含める。それ以外のCheckpoint参照先は接続を確認する。
2. 確認後、有効ルートに残る当日の画像も含め、対象が確定した元画像をarchiveへ退避する。対象に属する可能性がある未解決画像、移動失敗、書き込み中の画像が残る場合は廃棄を進めない。評価DBをロックせずに確認表示・退避を行う。
3. 退避結果と走査情報を再利用し、確認後に変わったルート設定、接続、未確認・変更範囲だけを再検査する。対象の画像生成・書き込みが続いていれば廃棄を保留する。画像保存ワークフローと排他を共有しないため、対象を書き込む生成を一時停止したことを確認してから最終段階へ進む運用を推奨する。検査の信頼性を確保できないときは対象範囲を再走査するか、廃棄を保留する。
4. [連携仕様書](HandpickerSuite_Integration.md)の最終確認と対象単位の排他を使い、評価が引き続き `delete` で、同じCheckpoint本体である場合に限り、ごみ箱へ移す。評価変更、ファイルの入れ替わり、退避未確認、再接続待ちなどで中止した場合も、退避済みの画像はarchiveに残す。
5. ごみ箱移動の成功後、処理対象のarchiveフォルダに `★` を付け、対応cacheを整理し、評価・予約・一覧を更新する。`★` は廃棄済みを示し、画像はエクスプローラーで閲覧できる。後処理の失敗は廃棄失敗と区別し、成功済みのごみ箱移動を再実行せずに再開できるようにする。

関連サイドカーの扱いと外部削除・復元時の扱いは第12章に示す。外部削除に伴うCyclerの既存の次候補選択を維持する。

### 8.4 ごみ箱利用上の制約

Studioは画像とCheckpointの両方で、ごみ箱への移動を確認できる経路を使う。ごみ箱を利用できない場合は削除を中止し、元ファイルを保持して理由を知らせる。UNC・ネットワークドライブ・大容量ファイルでのWindowsの挙動、取消時の項目別結果、復元先は実機で検証する。Studioによる完全削除への切り替えは設けない。

## 9. 代表サムネイル設定

画像一覧または個別ビューワの右クリックメニューから、選んだ元画像を縮小したJPEGをCheckpoint本体の隣へ保存する。

```text
Model_A.safetensors
Model_A.jpg
```

既存のサムネイルがあれば更新する。選定済みマーク、代表画像ID、専用の管理JSONは持たない。元画像の移動・削除後もコピー済みの代表画像は残る。

プロジェクト設定の「参照ルート」に続く「サムネイル」タブに「サムネイル一括登録」を配置する。保存済みの設定で走査した画像から、未設定の代表サムネイルを補う。サムネイルはボタンを実行した時点で保存する。既存のサイドカーは対応している別拡張子や別名も含めて保持する。所属が確定した画像のうちArchiveを優先し、同じ保存区分では相対パス順、同名の場合はフルパス順に、最初に読み込める画像を使用する。候補がないCheckpointと相対パスが重複するCheckpointはスキップし、保存結果を件数で表示する。一括登録中に標準の保存先へ別のサムネイルが作られた場合も上書きしない。

JPEG縮小仕様はCheckpointThumbnailExporterを参考にし、アスペクト比維持、拡大なし、最大辺・品質指定を基本とする。初期値案は最大辺512px、JPEG品質90。Exporterの管理用JPEGコメントは付与しない（Exporterのuninstall_managedによる手動選定画像の削除を防ぐ）。既存のHandpickerSuiteおよびOGN-ModelManagerのサイドカー参照規則に合わせる。既存の別拡張子サムネイルとの競合や再表示タイミングは詳細設計で確認する。

## 10. HandpickerSuiteとの評価情報連携

共有データ、プロセス間排他、外部変更の検知、削除予約と廃棄の契約、およびSuite側の改修範囲は[連携仕様書](HandpickerSuite_Integration.md)を参照する。

- Suiteの既存評価JSONを正本とする。各アプリの評価変更は即時保存し、全更新処理で共通排他と厳密な読込検証を使う。既存の評価値とfavorite互換情報を保つ。
- Studioの `delete` はドラッグ＆ドロップで付ける論理評価に限り、Suiteの削除予約を生成しない案とする。既存予約があれば、`delete` 解除時と廃棄完了時に失効させる。Studioからの直接遷移とSuite Taggerの従来の操作制約の併存は第12章の判断事項とする。
- Cyclerは候補抽出前に最新評価を取り込み、既存のタブ同期を活用する。本体の外部削除に伴う次候補選択、ワークフローの初期化やQueueの基本動作を維持する。

## 11. 非機能要件・異常系・受入観点

### 11.1 性能・操作性

- 一覧はcacheを利用し、表示範囲の仮想化・遅延読み込みを検討する。
- 大量画像の走査・JPEG生成・ネットワークアクセスでUIが操作不能にならないようにする。
- プロジェクト切り替えやルートOFF時に、旧対象の非同期処理が新しい画面へ結果を反映しないようにする。対象ルートをOFFにした場合は新たなファイル操作の開始も止め、進行中の操作はファイル単位の安全な境界で終了する。
- ファイル操作の進捗・失敗を把握できるようにする。数値性能目標は実測後に定義する。

### 11.2 安全性

元画像とcacheの削除処理を区別する。パスの正規化とルート内判定を実施し、ジャンクション・シンボリックリンク・ネットワーク切断・重複ルートを考慮する。生成中・書き込み中の画像は破損や誤移動を防ぐ。既存ファイルを無断で上書きしない（明示的な代表サムネイル設定を除く）。

### 11.3 主要受入テスト

| ID | 観点 | 期待結果 |
|---|---|---|
| T01 | プロジェクト切替 | 対象Checkpointと画像だけが表示される |
| T02 | 共通Output・同名モデル | AnimaとIllustriousの警告にプロジェクト名・safe名・フルパスが表示されてコピーできる。該当する画像は所属未確定で扱い、他プロジェクトの画像を変更しない |
| T03 | 複数ルート | 同じCheckpointの画像を統合表示。別ルートの同名画像が衝突しない |
| T04 | カードOFF/ON | OFFで表示・走査対象外、ONで再開。ファイルは失われない |
| T05 | ネットワーク切断 | 元画像の消失・走査完了・評価DB初期化とみなさない。ON・Offlineなら廃棄を保留し、再接続後に必要範囲を確認できる。OFFの存在だけで廃棄を禁止しない |
| T06 | 本日・過去画像 | Archive化で前日までの対象画像を移動し、本日のフォルダーや本日更新した画像はOutputに残る。cacheが有効なら両方のサムネイルを生成できる |
| T07 | 再走査 | 更新で参照先と画像の一覧を読み直す。次のArchive実行で、追加または前回移動できなかった過去画像を再判定する |
| T08 | 空ディレクトリ | Archive化・解除で空になった元フォルダーを子から親へ削除し、管理ファイルだけになったCheckpointのArchiveフォルダーも片付ける。参照ルート、他の画像・非画像ファイル、リンクを保持する |
| T09 | 画像閲覧・削除 | 左右キー・複数選択・Deleteで所定動作。確認なし、ごみ箱利用 |
| T10 | Checkpoint廃棄 | `delete` のみ確認後に実行可能。有効ルートの本日画像も退避し、ごみ箱移動完了後に★付与とcache整理を行う |
| T11 | 評価変更 | StudioとSuiteが評価を共有。次回Cycler実行で外部変更を反映 |
| T12 | 評価DBの同時更新 | StudioとTagger・Tag Import・Refresh Allの競合でも別Checkpointの評価を失わない。Importは排他下の最新値で既存の競合方針を適用する |
| T13 | 代表サムネイル | 元画像から既存規則のサイドカーJPEGを生成し、SuiteとOGN-ModelManagerで表示できる。管理用JPEGコメントがなく、Exporterの `uninstall_managed` の対象にならない。マークや専用DBを使わない |
| T14 | cache再構築 | cache・走査JSON消失後も元画像を保ったまま再構築でき、手動移動した画像の所属と重複保留が維持される |
| T15 | 異常系 | 移動・削除・JSON更新の失敗を成功扱いにしない。無断完全削除なし |
| T16 | safe変換衝突 | 同一プロジェクトの `a/b.safetensors` と `a_b.safetensors` を検出する。登録後の追加や大文字小文字だけの差も警告する。保存ノードによる `a__b` と `a_b` の衝突でも自動移動しない |
| T17 | 改名後の旧画像 | 片方を改名・登録解除しても旧safe名の画像は自動移動されない。手動で移動先プロジェクトを指定し、ファイル名で一意に照合できる画像を振り分けられる |
| T18 | 画像のプロジェクト間移動 | Output／archiveから単一・複数画像を選び、指定先のarchiveへ移動する。内容・メタデータ・評価を保持し、再走査しても元のプロジェクトへ戻さない |
| T19 | 同名衝突・部分失敗 | 既存画像は上書きせず、失敗分の元画像を保持する。別ボリュームでのコピー途中の切断、公開後の元画像除去失敗、再開時に喪失・重複適用がない |
| T20 | 退避中の `delete` 解除 | Suiteから評価を解除でき、Studioは本体を廃棄しない。退避済み画像はarchiveに残る |
| T21 | 廃棄対象の入れ替わり | 確認後、または最終処理と並行して同じパスが別ファイルに置換された場合も、その別ファイルを廃棄しない |
| T22 | 評価DB破損 | 不正形式・不明バージョン・アクセス不能でStudio、Tagger、Import、Refresh Allの全書き込みを中止し、元JSONと互換データを保持する |
| T23 | 削除予約の失効 | `delete` 解除と廃棄成功で対応する予約が失効する。確認待ちだったスクリプトは実行直前の再検証で対象を外し、同名の復元・再ダウンロードで古い予約が復活しない |
| T24 | 評価体系 | 6グループと既存アイコンを表示し、既存の `god` を他項目の編集・Import・再起動で保持する。Studioの `none` が次回Cycler実行に反映される |
| T25 | 廃棄・連携の途中終了 | 最終処理中に中断しても別モデルを削除しない。成功済みなら予約・cache・★付与を再開し、確定できない間は再廃棄しない。別Checkpointの評価変更は可能 |
| T26 | 実機でのごみ箱利用 | ローカル・UNC・ネットワークドライブ・大容量のCheckpointで、成功・未対応・キャンセル・部分成功を区別し、完全削除へ切り替わらない。復元先を確認する |
| T27 | 空のWPFアプリの配布確認 | 機能実装前に `--self-contained false` を明示してRelease発行し、Windows x64向けポータブルZIPを生成する。ZIPにランタイムを含まず、READMEに必要なランタイムとMicrosoft公式ダウンロード先を記載していることを確認する。.NET 10 Windows Desktop Runtime（x64）導入済みのWindows 11 x64で、標準ユーザーが書き込み可能な展開先から起動・終了できる |
| T28 | 再ビルド時のデータ保護 | 既存の設定・管理データを置いた展開先がある状態で、同一バージョンの再ビルドとビルド失敗を試す。展開先のデータ、archive、cache、共有評価DB・予約が保たれ、生成ZIPに既存のユーザーデータが含まれない。失敗時は直前の有効なZIPを保持する |
| T29 | Archive化・解除 | 全体・複数Checkpoint単位で実行し、当日更新・日付不明・所属未確定の画像を残す。実行を重ねた後も元のOutputへ戻し、外部へ取り出した画像と手動振り分けは対象外とする。競合時は同名画像を上書きせず、解除時は起動時の自動実行をOFFにする |
