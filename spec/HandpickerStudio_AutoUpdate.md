# HandpickerStudio 自動アップデート詳細設計

- 文書改訂番号：Rev. 1
- 対象アプリケーションバージョン：HandpickerStudio v0.1.0
- 基本方針：[基本設計書 §2.2 自動アップデート](HandpickerStudio_BasicDesign.md#22-自動アップデート)

## 1. 既存の保存先と変更範囲

現行ソースで `AppContext.BaseDirectory` を直接使う保存処理は次の3か所。

| 現行の処理 | 更新対応後 |
|---|---|
| `MainWindow.xaml.cs` の設定読み込み。実行ファイルの隣の `settings.json` にプロジェクト、重複保留、外観、ウインドウ位置、Archive設定、cache管理情報を保存 | ポータブルルートの `data/settings.json` を `SettingsStore` に渡す。設定形式とプロジェクト・cacheの識別子は引き継ぐ |
| `MainWindow.Archive.cs` の復帰用記録。実行ファイルの隣の `archive-history/` に保存 | ポータブルルートの `data/archive-history/` を使う。記録内のプロジェクトID・ルートID・画像パスは引き継ぐ |
| `WorkspaceSettings.cs` の既定cache。実行ファイルの隣の `cache/` を参照 | ポータブルルート直下の `cache/` を引き続き使う。設定された保存先と過去の管理先も保持する |

起動窓口は自分の実行ファイルがある場所をポータブルルートとする。本体は起動時に窓口から渡されたルートを検証し、保存先の決定に使う。内部の実行ディレクトリは、その版のDLLやリソースを参照する基準とする。通常の開発起動は従来の保存先で動作する経路を残し、自動更新の適用はポータブル構成で実行する。

```text
<ポータブルルート>/
  HandpickerStudio.exe       起動窓口
  app/
    versions/<version>/      版ごとのWPF本体と依存ファイル
    update/                  起動先の記録、更新作業領域、起動窓口の復旧用ファイル
  data/
    settings.json
    archive-history/
  cache/                     設定欄が空の場合のcache
```

既存の平置き版から取り込む場合は、本体と設定・Archiveの書き込みが停止していることを確かめ、`settings.json` と `archive-history/` の復帰用記録を作業領域にコピーして内容を検証する。旧配置のファイルを保持し、`data/` の既存データと競合する場合は案内して停止する。新版は作業領域のコピーを読み取り専用で起動確認し、確認後に取り込み先を確定する。取り込みの途中状態は更新記録に残し、再開時に重複して上書きしないようにする。Archiveの画像、cache、Suite側の評価DB・削除予約・廃棄記録は現在の参照先を維持する。

## 2. 起動確認と版の切り替え

1. 更新確認とダウンロードはバックグラウンドで行える。承認後も、実行中の画像操作、Archive化・解除、廃棄の後処理、サムネイル登録、評価の保存や取り込みが終わるまで待つ。メイン画面、プロジェクト設定、個別ビューワの稼働状態を集約し、切り替え開始後は新しい書き込み操作を受け付けない。他の起動中のインスタンスがあれば更新を延期する。本体の通常終了と保存完了を確認する。
2. 既に信頼済みの更新処理が署名済みZIPを検証し、別ディレクトリに新版を準備する。現在版への起動先を保持したまま、新版を検証用の状態で起動する。設定を読み取り専用で開き、必要な依存ファイルの読み込み、WPF画面とDispatcherの初期化、更新元への応答を確認する。
3. 検証用の状態では、通常の起動処理に含まれる重複保留の保存、Archiveディレクトリの作成、起動時Archive、cache生成・清掃、終了時のウインドウ位置保存も抑止する。画像移動・削除、評価保存などを実行できる画面操作は有効化しない。起動確認前に閉じた場合もユーザーデータは書き込まない。
4. 起動したプロセスの応答と対象版を確認してから起動先の記録を同一ボリュームで切り替え、新版に通常動作の開始を通知する。起動失敗や応答なしの場合は旧版を維持し、再起動時にも復旧できる状態を残す。応答がないプロセスは強制終了せず、必要なら通常の終了を待ってから旧版を起動する。次回起動は更新記録と稼働状態を照合して復旧する。

## 3. ビルドと署名鍵

現行の `build.ps1` はアプリケーションのVersionを取得し、新しい作業領域でFramework-dependent発行、ZIP生成、内容検証まで行っている。署名付き配布物の作成もこのスクリプトの配布モードにまとめる。普段のビルドでは署名鍵を要求しない。正式版と試験版の配布成果物はそれぞれ専用の出力先へ置く。

1. ビルド時の配布設定とVersionから、Windows x64ポータブルZIPを従来どおり生成・検証する。正式版ではアプリケーションのVersion、配布先、公開予定タグの一致を確認する。試験用のバージョン指定は試験ビルドに限定する。
2. 配布モードは検証済みZIPのバイト数とSHA-256から、製品ID、配布先、タグ、対象環境、ファイル名を含むマニフェストを生成する。マニフェストの出力バイト列にRSA-PSS/SHA-256で署名し、署名ファイルに鍵の識別子と署名を記録する。ZIP、マニフェスト、署名の組み合わせを組み込み公開鍵で再検証し、すべて成功した場合に配布用の一組として成果物へ移す。途中失敗時は直前の有効な成果物を保持する。公開時は三点を同じGitHub Releaseの下書きに添付してから公開する。 [RSA署名検証の .NET API](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.rsa.verifydata?view=net-10.0)・[GitHubの公開手順](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases#best-practices-for-publishing-immutable-releases)
3. 署名に使うRSA鍵は、署名担当者のWindowsユーザー証明書ストア `CurrentUser/My` に登録し、スクリプトは証明書の識別子で選ぶ。秘密鍵、PFXとそのパスワードはリポジトリ・成果物・ビルドログに含めない。正式版用と試験用は別鍵とする。復旧用に暗号化PFXをオフラインで保管し、パスワードを別経路で管理する。運用環境には原則としてエクスポート不可で登録し、別環境でバックアップの復元・署名・検証を確認する。 [Windows証明書ストアの管理](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/inspect-certificates-manage-certificate-stores)
4. 計画的な鍵変更では、次の公開鍵も認識できる版を現行鍵で配布し、移行期間中は一つの署名ファイルに旧鍵・新鍵の署名を入れる。初期版から、同じマニフェストに対して信頼済みの鍵で検証できる署名を選べるようにする。旧鍵の廃止後は未移行の利用者に手動更新を案内する。漏えいが疑われる鍵は移行用の署名に使わず、公式の案内で信頼できる最新版への手動更新を促す。本体・更新処理・起動窓口の全てで信頼する公開鍵をそろえる。

## 4. 起動窓口の更新と不要ファイルの整理

- 起動窓口はWindows x64向けのFramework-dependent単一ファイルを第一案とする。本体と分離し、ランタイムは従来どおり同梱しない。通常のアップデートでは版ごとの本体を切り替える。起動窓口の修正や公開鍵変更が必要な場合は、検証済みZIP内の起動窓口も更新する。 [Microsoftの単一ファイル配布](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)
- 起動窓口を更新する場合は、本体と現在の起動窓口が終了した後、別プロセスの更新処理が同一ボリュームで旧EXEをバックアップ付きで置き換える。新版の窓口が現行本体と復旧用の旧本体を起動できることを確認する。置き換え失敗・ロック・起動検証失敗時は旧窓口と旧版へ戻す。中断して窓口から起動できない場合に備え、検証済みバックアップの場所と手動復旧手順を配布文書に記載する。 [File.Replaceの動作](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=net-10.0)
- 正常起動が確定した後、現在版と直前の正常版を残し、更新処理が作成した古い版・一時ZIP・展開作業領域を整理する。起動窓口を更新した場合は、旧版を起動できる窓口も保持する。削除候補は更新記録で所有を確認し、ポータブルルートの更新管理領域内にある実パスを検証する。リンク、稼働中の版、用途が不明なファイル、ユーザーデータのパスは削除対象から除く。ロック等で削除できない場合は次の安全な機会に再試行する。

## 5. v0.0.0 から v0.1.0 への更新試験

### 試験用リリースの公開方法

試験用の公開GitHubリポジトリを公式リポジトリと分ける。試験ビルドには試験用リポジトリ、試験用公開鍵、アセット名の試験用接頭辞をビルド時に固定し、画面とZIP名に試験用であることを表示する。正式ビルドは公式リポジトリと正式公開鍵に固定し、実行時の設定や起動引数で試験用へ切り替える機能は設けない。

両方のビルドで `/releases/latest` の応答、通常リリースの扱い、現行より新しい版かどうか、署名およびZIPの検証に同じ実装を使う。試験用リポジトリでは、更新機能を含む `v0.0.0` と `v0.1.0` を順に通常リリースとして公開する。タグと各実行ファイルのバージョンを一致させ、それぞれのZIP・マニフェスト・署名を同じリリースに添付する。正式リポジトリのタグ、Latest、配布資産には試験用成果物を載せない。 [GitHub ReleasesのLatest判定](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)

### 試験手順

1. .NET 10 Windows Desktop Runtime（x64）導入済みのWindows 11で、標準ユーザーが書き込める専用フォルダーへ試験用 `v0.0.0` を展開する。実運用と分けたテスト用の設定、プロジェクト、重複保留、Archiveの復帰用記録、画像、cache、Suite側の共有データを用意し、内容・配置・ハッシュを控える。
2. `v0.0.0` がLatestの間に、同じ版を更新候補としないことを確認する。`v0.1.0` を下書きにした段階でも候補に出ないことを確かめる。試験用 `v0.1.0` をLatestとして公開し、`v0.0.0` の起動時確認と手動確認で候補が出ることを確かめる。自動確認をOFFにしても手動確認できること、辞退した場合に版が切り替わらないことを確認する。
3. 更新を承認し、正常終了後に同じ `HandpickerStudio.exe` から `v0.1.0` が起動することを確認する。起動検証中はデータ操作を試みても書き込みが発生しないことを確認する。更新前のテストデータと照合し、プロジェクト切り替え、画像閲覧、Archiveの復帰、評価参照が引き続き動作し、`v0.0.0` が復旧用に残ることを確認する。
4. 同じ `v0.0.0` のZIPを別の専用フォルダーに再展開し、プレリリースや古い版の除外、通信断、正式版と試験版の署名の取り違え、ZIP・署名の不一致、サイズやパスの不正、処理中・ファイルロック、起動確認の失敗、切り替え中断を個別に試す。異常応答や破損ファイルはローカルの試験データを使い、公開したZIPは入れ替えない。失敗時の旧版起動とユーザーデータ維持を確認する。起動窓口を置き換える場合の失敗・途中終了も検証する。
5. 旧配置の取り込みは別の試験用フォルダーで検証する。ローカルで管理対象の正常版を3世代用意した追加試験で、現行版・直前版・復旧用の起動窓口を残し、それより古い管理対象と一時ファイルだけが整理されることを確かめる。

## 6. 他アプリへの転用

更新情報取得、署名検証、版の切り替えは、Studioのプロジェクト・画像・Suiteのデータ形式に依存させない。製品名、固定の配布先・公開鍵、保存先、終了可能かどうかの判断は製品側に置く。OpenGepaへ転用するときに、実際に共通になった部分を切り出す。
